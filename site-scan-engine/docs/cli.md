# CLI

**Who this is for:** the people who run scan tools (`seo-scan`, `jsonld-scan`, …) and the authors who wire `runCli`. The CLI is the
product's UI and the only documented way to use the engine; `Engine` stays exported for tools that need their own orchestration.

Related: [configuration](configuration.md) · [architecture](architecture.md) · [formats](formats.md)

## Commands

| Command | What it does |
| --- | --- |
| `<tool> scan` | Fetch every site once, run the checks, write the reports. `--resume <run>` continues an interrupted run. |
| `<tool> report <run>` | Rebuild the reports of a finished run from its stored config. No network. `--reporters a,b` overrides the list for this call only. |
| `<tool> validate` | Resolve config, plugins, option schemas, the run store and the sites; print the plan; fetch nothing. Same as `scan --dry-run`. |
| `<tool> plugins` | List every available plugin (sources, adapters, reporters, extensions, stores) with engine range, description and options. |

`<tool> <command> --help` prints the options of one command; it is generated from the flag table below.

## What you see during a run

Three stages, always in this order. Everything except the final file list goes to **stderr**; colour is never the only signal.

**1. Plan**, printed before the first request so you can Ctrl+C before anything happens:

```
seo-scan · engine 0.2.0

  Sites      2,413 from sites.local.csv  →  2,301 after filter "public"  (112 skipped: 97 private, 15 inactive)
  Pages      4,602  (2 paths: /, /tee-times/)
  Checks     seo, health
  Fetching   3 in parallel · 300 ms pause · 15 s timeout · retry ×2
  Extensions host-map
  Output     reports/seo-scan-20261013-142501  →  results-csv, findings-csv, summary-md
  Estimate   < 1 h  (from concurrency and pause)
```

On `--resume` the plan adds `Resuming   1,940 already done, 2,662 left`.

**2. Progress.** On a TTY one live line, redrawn at most every 200 ms:
`▕██████████░░░░░░░░░░▏ · 48% · 2,212/4,602 · 2.1 p/s · ETA 18m 54s · ✓ 2,180 ✖ 32 · findings: 410 err 1,022 warn`.
When piped (CI) one plain line every 5 % or 30 s. Notable events print **above** the live line: the first fetch failure of each
type (the rest are counted), every adapter crash, and the first 5 warnings.

**3. Summary**: duration, pages, ok / failed, findings by severity with the top codes, failure types, the reports written, and at
most one `Next` suggestion — `--resume` after an interrupt, or `--from-run … --code engine.fetch_failed` when pages failed (non-2xx pages are `engine.http_status` warnings and do not count as failed).
If `--fail-on` was reached it ends with `✖ Threshold "error" reached → exit 2`.

### Output levels

| | Plan | Live progress | Notable events | Warnings | Summary | stdout |
| --- | --- | --- | --- | --- | --- | --- |
| default | yes | yes | first per type | first 5, then counted | yes | files + run location |
| `--quiet` | — | — | — | — | — | files + run location |
| `--verbose` | yes | yes + a line per page | all | all | yes + adapter timings | files + run location |
| `--json` | `plan` event | `progress` events | `notable` events | `warning` events | `summary` event | NDJSON only |

### stdout contract

stdout carries only the files the reporters wrote and, **last**, the run location — so `$(tool scan … | tail -1)` yields it.
With `--json` stdout is NDJSON only.

### Ctrl+C

One Ctrl+C stops gracefully: `Stopping… finishing 3 pages in flight (Ctrl+C again to force)`; the reports are still written and
the summary suggests `--resume`; exit code `130`. A second Ctrl+C exits immediately with `130`; only records already appended are
kept (they are durable), and no reports are written.

## `--json`

One JSON object per line on stdout: `{ "type": …, "ts": …, …payload }`. stderr stays empty except for an internal bug (the
stack). The payloads are the same view models the human output renders — there is no separate data model.

| `type` | When | Payload |
| --- | --- | --- |
| `plan` | before the first request | tool, engine version, sites (loaded / filtered / excluded), pages, paths, checks, fetching, extensions, output, estimate, resume |
| `target` | a page finished | `done`, `total`, `siteId`, `path`, `status`, `timingMs`, `error` |
| `progress` | after each page | `done`, `total`, `elapsedMs`, `ok`, `failed`, `errors`, `warnings` |
| `notable` | a fetch failure or adapter crash | `kind` (`fetch`\|`adapter`), `message`, `errorType?` |
| `warning` | a non-fatal problem | `source`, `message` |
| `interrupted` | first Ctrl+C | `inFlight` |
| `summary` | the end | duration, pages, ok, fetchFailed, findings, topCodes, failureTypes, written, location, warningCount, adapterTimings, interrupted, threshold, next |
| `report` | `report` finished | `written` |
| `validated` | `validate` / `--dry-run` finished | `ok: true` |
| `plugins` | `plugins` | `groups` of plugins with their option schemas |
| `config` | `validate --verbose` | `entries`: `path`, `value`, `origin` |
| `error` | the command failed | `code` (an `ErrorCode`), `problems`, `command` |

## Errors

Input is validated before anything is fetched, and **all** problems are shown together:

```
✖ Invalid input (3 problems)

  --concurency
    Unknown flag. Did you mean --concurrency?

  --timeout -1
    "-1" is not an integer >= 1.
    Use a whole number >= 1.

  --from-run
    Requires --code or --exclude-code.
    Example: --from-run reports/old --code engine.fetch_failed

Run `seo-scan scan --help` for all options.
```

Every message says what is wrong, where (the flag, `file → key = value`, or `tool default`) and how to fix it; unknown commands,
flags, config keys, enum values and plugin ids get a "did you mean" (edit distance ≤ 2). No stack traces for user mistakes. Anything
that is not a user mistake is shown as `Unexpected error` with its stack and a request to report it.

### Error codes

Stable; also the `code` of the `--json` `error` event.

| Code | Meaning |
| --- | --- |
| `unknown_command` | The command does not exist. |
| `unknown_flag` | The flag does not exist. |
| `flag_not_for_command` | The flag exists but not for this command. |
| `bad_flag_value` | Missing, malformed or out-of-range value, or a flag given twice. |
| `missing_required_flag` | A flag needs another flag (`--from-run` needs `--code`), or a command needs its argument. |
| `conflicting_flags` | Two flags that exclude each other. |
| `config_file_unreadable` | `--config` could not be read or parsed. |
| `config_invalid` | The merged config has problems (shape, ranges, removed keys, plugin options). |
| `plugin_invalid` | A plugin failed its `define*` checks. |
| `plugin_incompatible` | A plugin's `engine` range does not match, or resume with different adapters. |
| `unknown_plugin_id` | An unknown source, reporter, extension or store id. |
| `source_failed` | The site source threw. |
| `no_sites_selected` | The source has nothing to load (missing `path` / `urls`). |
| `run_not_found` | `--resume`, `report` or `--from-run` points at no run. |
| `run_already_exists` | The `--out` location already holds a run. |
| `run_schema_unsupported` | The run was written with an unsupported `recordSchemaVersion`. |
| `reporter_failed` | A reporter failed (the others still ran). |
| `internal_error` | A bug in the tool or the engine. |

### Exit codes

| Code | Meaning |
| --- | --- |
| `0` | OK. |
| `1` | Usage, config or runtime error, or a reporter failed. |
| `2` | `failOn` threshold reached. `engine.http_status` is a `warning`, so only `--fail-on warning` counts non-2xx pages; `error` is reserved for pages that could not be scanned. |
| `130` | Interrupted with Ctrl+C. |

## Colour

On for a TTY. `NO_COLOR=1` or `--no-color` turns it off; `FORCE_COLOR=1` turns it on for a pipe. `NO_COLOR` wins over `FORCE_COLOR`.

## Wiring a tool

```ts
#!/usr/bin/env node
import { runCli } from '@cet/site-scan-engine';
import { seoAdapter } from './adapters/seo.js';

process.exitCode = await runCli({
    name: 'seo-scan',
    version: '1.4.0',
    adapters: [seoAdapter],
    // sources: [...], reporters: [...], extensions: [...], stores: [...]
    config: { scan: { paths: ['/', '/tee-times/'] }, output: { dir: './reports' } },
});
```

`RunCliOptions` also takes injectable `stdout`, `stderr`, `env`, `signals`, `now`, `clock` and `cwd`, which is how the tests drive
the CLI without a real terminal or process signal.

## Workflows

```bash
# 1. Export the site list once (never commit it; *.local.csv is gitignored)
wp site list --fields=blog_id,url,public,archived,spam,deleted,blogname --format=csv > sites.local.csv

# 2. Check what would happen, fetching nothing
seo-scan validate --sites sites.local.csv --filter public

# 3. Spot check one URL
seo-scan scan --url https://example.com/ --verbose

# 4. Full run over public sites
seo-scan scan --sites sites.local.csv --filter public

# 5. Re-scan only what failed
seo-scan scan --sites sites.local.csv --from-run reports/seo-scan-20261013-142501 --code engine.fetch_failed

# 6. Re-scan everything except what was already fine in an earlier run
jsonld-scan scan --sites sites.local.csv --filter public --from-run reports/jsonld-scan-<ts> --exclude-code jsonld.ok
# --code and --exclude-code combine (had A and none of X); the same code in both selects nothing.
# The run stores the concrete site list, so --resume works even if the earlier run is deleted.

# 7. Rebuild reports with another reporter, no network
seo-scan report reports/seo-scan-20261013-142501 --reporters results-csv,json

# 7. Continue an interrupted run
seo-scan scan --resume reports/seo-scan-20261013-142501

# 8. Compare production with staging (same siteIds, different hosts)
seo-scan scan --config staging.json   # staging.json enables the host-map extension
```
